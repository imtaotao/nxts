## 目标与边界

本规范定义前端源码快照、文件身份、位置范围、诊断结构、错误恢复预算和确定性输出。

文件扩展名与模块解析由[程序与模块](../../language/modules/1-moduleTypes.md)定义，Babel 节点位置由[Babel AST 契约](./2-babelAstContract.md)定义，前端停止与继续条件由[前端流水线](./1-frontendPipeline.md)定义。本规范不重新定义语言错误条件，只规定各阶段如何表达和交付错误。

## 源码快照

一次解析只读取不可变源码快照。快照至少包含：

| 信息         | 用途                               |
| ------------ | ---------------------------------- |
| FileId       | 当前程序内稳定引用同一逻辑文件。   |
| 规范路径     | 模块身份、诊断关联和缓存。         |
| 显示路径     | 面向用户输出，不参与模块相等判断。 |
| 源码文本     | Babel 输入、源码切片和诊断展示。   |
| BOM 状态     | 应用源码修复时保持原有 BOM 风格。  |
| 内容版本     | 区分同一路径的不同文本快照。       |
| 内容哈希     | 缓存校验和增量复用。               |
| 行起始索引表 | 将 UTF-16 偏移转换为行列位置。     |

源码文本、内容版本和行起始索引在快照创建后不可修改。文件发生变化时创建新快照，不能原地替换文本并继续复用旧 AST、NodeId 或语义侧表。

### 编码与换行

- 文件系统源码只接受 UTF-8 编码。
- 文件开头允许一个 UTF-8 BOM；解码前移除 BOM，并在源码快照中记录 `hadBom`。
- 非法 UTF-8 字节产生源码诊断，不能用 Unicode replacement character 静默替换后继续编译。
- 不接受 UTF-16、GBK 或依赖系统区域设置的其他源码编码。
- 解码后不规范化 Unicode，也不改写 `LF`、`CRLF`、单独 `CR`、`U+2028` 或 `U+2029`。
- Babel、NodeId 和 SourceSpan 使用移除 BOM 后的完整 JavaScript UTF-16 字符串；内容哈希直接使用移除 BOM 后的原始 UTF-8 字节。
- 行起始索引识别 ECMAScript 行终止符，其中 `CRLF` 作为一次换行处理。

自动修复写回文件时必须保持 `hadBom` 和原有换行内容；修复本身需要插入换行时采用当前文件检测到的主导换行风格。

## 文件身份

FileId 是一次程序构建或分析会话内的紧凑文件身份，不属于模块公开名称，也不能跨进程持久化为稳定 ABI。

- FileId 按规范路径在会话内分配连续整数，同一路径的不同源码版本保持同一 FileId。
- SourceVersion 是每个 FileId 独立单调递增的整数；内容实际变化时创建新版本，内容未变化时复用原快照。
- ContentHash 使用 SHA-256 计算移除 BOM 后的原始 UTF-8 字节，保留原始换行和 Unicode 形式。
- 同一规范路径在同一程序中只有一个当前源码快照。
- `(FileId, SourceVersion)` 唯一标识可被解析的文本版本。
- 显示路径变化不能改变模块身份。
- 大小写、符号链接、路径分隔符和相对段的规范化由模块解析与 Host 共同定义。
- 持久缓存使用规范路径、ContentHash、编译选项和工具链契约版本，不只使用 FileId 或 SourceVersion。

## 源码范围

前端统一使用 UTF-16 半开区间：

```text
SourceSpan = (FileId, SourceVersion, start, end)
```

其中 `start` 和 `end` 是指定源码版本中的 UTF-16 code unit 偏移，满足 `0 <= start <= end <= source.length`。

- 零长度范围用于缺失 token、文件末尾或无法覆盖现有字符的插入点。
- 主范围必须位于单个源码文件；跨文件关系使用多个范围表达。
- Babel 的 `start`、`end` 和 `range` 必须转换或验证为同一 SourceSpan。
- 行列位置按需从行起始索引计算，不作为语义身份或缓存主键。
- 诊断修复和源码切片必须引用产生该范围的 SourceVersion，不能套用到其他文本版本。

## 诊断模型

每条诊断至少具有：

| 字段        | 含义                                                  |
| ----------- | ----------------------------------------------------- |
| code        | 稳定的 Nxts 诊断码。                                  |
| severity    | 错误、警告或信息级别。                                |
| messageId   | 与诊断原因绑定的稳定消息模板身份。                    |
| arguments   | 用于本地化渲染的结构化消息参数。                      |
| primarySpan | 最主要的源码范围。                                    |
| labels      | 当前或其他文件中的补充范围与说明。                    |
| notes       | 不绑定范围的原因、类型展开或兼容性说明。              |
| fixes       | 可选且经过版本校验的源码修改建议。                    |
| phase       | Parser、Validator、Binder、Checker 或 HIR Validator。 |

Babel `ParseError`、内部异常或第三方错误对象不能直接作为公开诊断。每个阶段必须映射为稳定 Nxts 诊断码和 SourceSpan。

### 错误传递与宿主处理

用户源码、编译配置、模块解析和其他可预期失败必须通过不可变分析结果返回结构化诊断。Parser、Validator、Binder 和 Checker 的公开 API 不得因为用户输入不合法而向调用方抛出异常；能够恢复时同时返回 AST、tokens 或部分语义侧表，并明确标记结果是否完整。

| 调用方     | 处理方式                                                              |
| ---------- | --------------------------------------------------------------------- |
| 编译器 CLI | 渲染终端消息；存在 `error` 时返回失败状态，并且不生成 Checked HIR     |
| 编辑器服务 | 按 SourceVersion 发布诊断，保留可恢复结果用于高亮、查询和修复建议     |
| 测试工具   | 直接断言诊断码、参数、严重级别和源码范围                              |
| 构建系统   | 可以把 warning 视为构建失败，但不能改变诊断原始严重级别或类型检查结论 |

上层可以决定诊断的展示、筛选和交互方式，但不能降级语言 `error`、把不完整分析当作成功，或绕过 `error` 生成 Checked HIR。

用户主动取消分析属于控制结果，不产生源码诊断。NodeId 冲突、侧表损坏和其他前端内部契约破坏属于实现错误，可以使用异常通道；CLI 或 language service 必须在最外层捕获并记录此类故障，不能把内部异常对象伪装成用户诊断，也不能使编辑器宿主进程崩溃。

### 诊断码

诊断码使用 `NXT` 前缀和四位数字，并按主要职责划分：

| 范围      | 主要来源                   |
| --------- | -------------------------- |
| `NXT0xxx` | 源码读取、配置与前端预算。 |
| `NXT1xxx` | Parser 与语法验证。        |
| `NXT2xxx` | Binder、模块与名称解析。   |
| `NXT3xxx` | 类型检查与类型关系。       |
| `NXT4xxx` | 控制流、常量与副作用分析。 |

同一诊断码的根本原因和参数语义必须稳定；仅文案改善不创建新诊断码。错误从一个内部阶段迁移到另一个阶段时，只要用户可观察原因未变化，就保持原诊断码。

### 严重级别

- `error` 阻止生成 Checked HIR。
- `warning` 不阻止生成产物，但必须保持确定性且默认可见。
- `info` 只表达独立的非错误信息；从属于错误的解释使用 note，不产生额外顶层诊断。
- 编译器内部契约损坏不是用户诊断，必须进入独立的实现错误通道。

调用方不能把语言 `error` 降级。构建工具可以采用“warning 视为失败”的策略，但不能修改诊断对象中的原始 severity 或使 checker 产生不同类型结果。隐藏 warning 只影响展示，不改变分析结果。

### 消息渲染

Checker 和其他前端阶段输出 code、messageId、结构化 arguments 与源码范围，不把本地化后的最终文本作为诊断身份或缓存键。arguments 不能暴露可变 AST、内部错误对象或生命周期短于诊断结果的 TypeId。

终端、编辑器和测试工具使用同一消息目录渲染中文、英文或其他语言。测试优先断言 code、arguments、severity 与 SourceSpan；本地化文本使用独立快照测试。

### Labels 与 notes

每个 label 包含 SourceSpan、messageId 和结构化 arguments，可以指向当前文件或其他文件。primarySpan 表达主要错误位置，labels 表达原声明、冲突来源、推导位置或跨模块关联。

notes 只包含 messageId 和 arguments，用于不适合绑定源码范围的原因、类型展开或兼容性解释。label 和 note 都是主诊断的一部分，不单独计为顶层诊断。

核心诊断模型不再定义独立的 related information 字段。编辑器协议适配层将跨文件 label 映射为对应的 related information，避免维护两套关联范围。

## 错误恢复与连锁诊断

Parser、Validator、Binder 和 Checker 可以在错误后继续分析，但必须标记错误来源和污染范围。

- 同一根因不能由不同阶段重复报告等价消息。
- 内部 ErrorType 或错误符号只用于抑制连锁诊断，不产生新的语言兼容结论。
- 依赖错误值才能成立的后续诊断默认抑制；与错误节点无关的兄弟节点继续检查。
- 达到恢复预算后停止当前范围的新增普通诊断，并产生一次预算耗尽摘要。
- 无法恢复的 Parser 错误停止当前文件；其他文件仍可继续分析并报告独立错误。

## 诊断预算

error 与 warning/info 使用独立预算，避免大量 warning 阻止真正错误：

| 范围     | error | warning/info |
| -------- | ----: | -----------: |
| 每个文件 |   100 |          100 |
| 整个程序 |  1000 |         1000 |

label、note 和 fix 属于主诊断，不单独计数。调用方可以调整默认预算，但每种严重级别的全程序硬上限为 10,000；处理不可信源码时不提供无限模式。

达到预算后的行为：

- 达到单文件 error 预算后，停止该文件的进一步普通错误诊断，标记该文件分析不完整；其他独立文件继续检查。
- 达到全程序 error 预算后，停止后续普通错误诊断，标记整个程序分析不完整，并禁止生成 Checked HIR。
- 达到 warning/info 预算只停止生成对应非错误诊断，所有影响正确性的 error 检查继续。
- 未完成检查的节点返回“分析结果不可用”，不能伪装成合法类型、`unknown` 或正常 ErrorType。
- 每个耗尽的范围和严重级别产生一条 `NXT0xxx` 摘要，并在结果中设置 `diagnosticsTruncated`。

预算限制的是诊断生成和错误后的深入分析，不是先生成全部诊断再隐藏。调用方可以在修复已显示错误后重新检查，或在硬上限内提高预算。

## 确定性排序与去重

并行解析或检查不能改变诊断顺序。最终结果按以下稳定键排序：

1. 规范路径的非区域化顺序。
2. primarySpan 起始和结束偏移。
3. severity 顺序：error、warning、info。
4. 稳定诊断码。
5. 固定阶段顺序和阶段内产生顺序。

code、severity、primarySpan、messageId 和规范化 arguments 完全相同的诊断合并为一条，labels、notes 和 fixes 取确定性并集。不同根因即使消息文本相同也不能仅按文本去重。

## 修复建议

修复由一组带 SourceVersion 的非重叠文本编辑组成。应用前必须验证：

- 文件身份与内容版本未变化。
- 每个编辑范围合法且互不重叠。
- 同一修复中的多文件编辑全部可应用，否则整体拒绝。
- 修复不承诺一定使程序通过检查，但不能产生超出 Nxts 语法范围的源码。

每个修复标记 applicability：

| applicability    | 处理                                               |
| ---------------- | -------------------------------------------------- |
| `safe`           | 编译器可以证明修改保持目标语义，允许工具自动应用。 |
| `requiresReview` | 修改可能需要用户选择或改变意图，只能作为交互建议。 |

修复基础结构支持单文件和原子多文件编辑，但诊断不要求必须提供修复。只有能够建立可靠范围和修改结果的规则才生成修复；Parser 恢复节点或不可信范围不提供修复。

## 公开结果

前端诊断结果是一次分析的不可变快照，并明确提供程序及各文件的 `diagnosticsTruncated` 与分析完整状态。调用方可以按文件、严重级别和诊断码筛选，但筛选不能改变编译是否成功的判定。

公开结果不暴露可变 Babel error、内部异常对象、ErrorType、错误符号或阶段私有缓存。终端、编辑器和测试工具消费同一结构化诊断，再决定显示格式。

## 性能约束

- 每个源码快照只建立一次行起始索引。
- SourceSpan 使用紧凑 FileId 与 UTF-16 偏移，不复制源码片段。
- 消息文本和源码摘录按需格式化，不在热路径提前构造。
- 去重使用结构化键，不执行全量消息字符串比较。
- 诊断预算必须防止恶意源码造成无界内存与检查时间。
