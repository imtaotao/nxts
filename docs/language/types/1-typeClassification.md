# 类型分类与术语

- 规范状态：已定稿
- 实现状态：未实现
- 最后更新：2026-07-24
- 文档顺序：1

## 目标

定义 Nxts 类型系统使用的分类维度和公共术语，为类型检查、运行时表示及后续类型能力规范提供统一基础。

## 核心原则

类型的语言语义、构造方式和运行时表示是相互独立的维度：

| 维度         | 职责                                       |
| ------------ | ------------------------------------------ |
| 语言类型分类 | 定义源码中的类型具有什么值语义和可用能力   |
| 类型构造方式 | 定义类型是内建原子类型，还是由其他类型组成 |
| 运行时表示   | 定义值如何存储、传递、判别和被 GC 扫描     |

语言类型分类不能由运行时表示反向推导。两个类型可以使用相同的底层表示而保持不同的语言语义；一个基础值类型也可以使用 GC 引用表示。

例如，`string` 是不可变的基础值类型，但运行时可以使用指向 GC 对象的引用。该实现方式不会使 `string` 获得普通对象的可变性、属性身份或引用相等语义。

Nxts 源码必须保持 TypeScript 语法可解析。Nxts 当前接受的源码应当能够作为 TypeScript 风格源码被解析；Nxts 可以比 TypeScript 更严格，拒绝 TypeScript 接受但无法静态高效编译的写法。

Nxts 对已有 JavaScript / TypeScript 能力的可观察行为统一以 ECMAScript 严格模式为兼容基线，不支持仅在非严格模式成立的隐式全局变量、静默失败、`this` 替换、参数与 `arguments` 别名等语义。能够在编译期确定的严格模式错误应优先成为编译错误；具体语法入口和失败规则由对应能力规范定义。

性能是 Nxts 的第一目标。TypeScript 严格子集是源码兼容边界，不是牺牲固定布局、零隐藏成本和可预测 ABI 的理由。当 TypeScript 习惯写法与静态高性能编译目标冲突时，Nxts 应拒绝该写法或要求显式表达成本。

## 语言类型分类

### 基础值类型

基础值类型由语言直接内建，不通过其他类型组合产生：

```text
boolean
number
string
null
undefined
```

- `boolean` 只包含布尔值。
- `number` 表示具有 JavaScript Number 语义的数值。
- `string` 表示不可变字符串值。
- `null` 和 `undefined` 是相互独立的类型和值。

各类型的运算、兼容和运行时规则由对应能力规范定义。

### 原生标量类型

原生标量类型是 Nxts 为确定布局和原生性能增加的类型：

```text
i8 i16 i32 i64
u8 u16 u32 u64
f32 f64
usize isize
```

原生标量类型不是 JavaScript 基础类型，也不因使用相同的 LLVM 表示而自动成为 `number` 的别名或子类型。`number` 与 `f64` 当前是不同语义类型；二者之间的显式转换由数值类型规范定义。

原生标量类型由 Nxts 编译器内建识别，不依赖用户声明或标准库导入。TypeScript 侧声明只用于开发者体验和外部工具识别这些类型名，其形式由后续工具链规范定义，不影响 Nxts 的类型语义、运行时表示、数值转换、溢出规则或 ABI。

### 特殊类型

特殊类型参与静态类型检查，但不作为普通运行时值类型使用：

```text
void
never
```

- `void` 表示没有可供调用方使用的结果。
- `never` 表示控制流不会正常产生值。

二者的合法位置、类型关系和控制流规则由特殊类型规范定义。

### 字面量类型

字面量类型描述基础值类型或原生标量类型中的单个确定值：

```ts
true;
('ready');
200;
```

字面量类型不引入独立运行时表示，其值使用对应基础类型或原生标量类型的表示。字面量保留、扩大和推导规则由字面量类型规范定义。

### 复合类型

复合类型由一个或多个其他类型构造产生。Nxts 类型系统需要为以下复合类型明确支持或拒绝规则：

| 类型         | 示例                      |
| ------------ | ------------------------- |
| 对象类型     | `{ x: i32; y: i32 }`      |
| 字典类型     | `{ [key: string]: i32 }`  |
| 接口契约     | `interface Entity`        |
| 函数类型     | `(value: i32) => boolean` |
| 数组类型     | `i32[]`                   |
| 元组类型     | `[i32, string]`           |
| 联合类型     | `string \| undefined`     |
| 交叉类型     | `A & B`                   |
| 泛型实例类型 | `Array<i32>`              |
| 幻象品牌类型 | `Brand<i64, "UserId">`    |
| 类实例类型   | `User`                    |

列入分类不代表对应能力已经被支持。每种复合类型只有在其规范标记为已定稿并纳入当前语言版本后，才属于可接受的源码类型。

## 类型声明与类型身份

类型声明为类型或类型构造器引入名称。声明语法与类型身份是不同概念：

| 声明形式    | 分类边界                                                    |
| ----------- | ----------------------------------------------------------- |
| `type`      | 为类型表达式提供名称，本身不自动创造新的运行时类型身份      |
| `interface` | 声明结构化多态契约；值进入接口位置时形成接口视图            |
| `class`     | 同时声明具有运行时身份的构造能力和实例类型                  |
| `enum`      | 声明封闭名义标量类型；值使用 `i32` 或字符串表示，空枚举无值 |

`type` 对象描述精确的具体对象形状；`interface` 描述可以由不同具体对象或类满足的结构契约。二者即使成员文本相同也不是同一类语义类型。别名展开、接口归一化、类身份和递归声明的具体规则由对应规范定义。

`Brand<T, Tag>` 是 T28 定义的专用静态类型构造器。它保留区别于 `T` 的语义类型身份，但沿用 `T` 的语言类型分类和运行时表示，不创建运行时对象、字段或 tag。普通 `type` 声明仍然透明。

## 类型级能力

类型级能力用于查询、构造、约束或检查类型，本身不是运行时值类型：

```text
keyof
类型查询
索引访问类型
as const
satisfies
条件类型
映射类型
infer
模板字符串类型
```

每项类型级能力必须明确标记为支持或不支持。parser 和 checker 不能因为某项能力属于合法 TypeScript 语法就默认接受。

`keyof`、类型查询、索引访问类型和 `as const` 已由 [T40](./26-typeOperators.md) 定稿；条件类型、映射类型、`infer` 和模板字符串类型已由 [T41](./27-advancedTypes.md) 定稿；`satisfies` 由 T42 定义。

## 当前无效与预留类型

当前规范标记为不支持的类型不进入 Nxts 当前版本的有效类型集合：

- `any` 永久不支持。
- `bigint` 当前不支持。

parser 或 converter 可以识别相应 TypeScript 语法以产生明确诊断，但不得为其创建可继续通过 checker 的有效 Nxts 类型。

`unknown` 是有效的显式安全动态值类型，不属于隐式顶层类型。普通值必须经过显式表示转换才能进入 `unknown`，其合法操作与运行时边界由 T17 定义。

`symbol` 是有效的不透明身份基础类型，`unique symbol` 是绑定声明身份的单例下位类型。当前只支持值身份能力；symbol 属性键和 JavaScript 元编程协议由 T18 明确预留但不开放。

## 运行时表示分类

类型层只记录后续布局规划所需的表示需求，不决定机器字宽、字段、tag、payload、niche 或传参方式：

| 表示需求         | 典型类型                             | 类型层提供的事实                                   |
| ---------------- | ------------------------------------ | -------------------------------------------------- |
| 标量值域         | `boolean`、数值、`symbol`            | 值域、身份和合法运算。                             |
| 管理存储         | `string`、对象、数组、类实例         | 是否具有引用身份、是否不可变以及是否需要 GC 管理。 |
| 静态视图         | `readonly`、品牌、透明别名           | 与来源值的表示关系必须是无操作，且不创建新身份。   |
| 契约视图         | 接口、对象字典视图                   | 必须保留底层对象身份，并携带静态已选契约。         |
| 复合值           | 元组、函数值、联合                   | 成员、位置、状态和调用约束。                       |
| 零载荷或不可构造 | `null`、`undefined`、`void`、`never` | 是否可存储、是否可正常产生值以及是否具有载荷。     |

具体物理分类和布局由 [`1-typeRepresentation.md`](../../compiler/representation/1-typeRepresentation.md) 唯一定义，跨模块传递由 [`1-typeAbi.md`](../../compiler/abi/1-typeAbi.md) 定义。表示优化必须保持类型规范定义的全部可观察行为。

## 公共术语

| 术语         | 定义                                                     |
| ------------ | -------------------------------------------------------- |
| 类型         | 描述表达式可能产生的值集合以及允许执行的操作             |
| 值语义       | 程序能够观察到的值行为                                   |
| 运行时表示   | 编译后用于存储、传递和判别值的数据布局                   |
| 类型身份     | 两个类型是否被类型系统视为同一个类型                     |
| 类型表达式   | 源码中描述类型的语法结构                                 |
| 类型声明     | 为类型或类型构造器引入名称的声明                         |
| 类型构造器   | 接受其他类型并产生复合类型的能力                         |
| 规范类型     | checker 完成别名展开和结构归一化后使用的 canonical type  |
| 类型视图     | 不改变运行时表示，只改变可见能力或写权限的静态类型       |
| 接口视图     | 保留底层对象身份，并附带契约访问所需见证表的运行时值     |
| 字典视图     | 保留底层对象身份，并附带动态索引访问所需见证表的运行时值 |
| 有效类型集合 | 当前语言版本允许进入 checker 和后续编译阶段的类型集合    |

## 编译器边界

编译器内部应分别保存语言类型信息和运行时表示信息：

```text
源码类型表达式
  -> 名称解析与类型构造
  -> 规范类型
  -> 类型检查与控制流分析
  -> Typed IR 类型与表示分类
  -> 目标平台布局和 ABI
```

- parser 和 converter 负责保留或归一化受支持的类型语法，并拒绝当前不支持的类型节点。
- checker 使用规范类型执行类型相等、兼容、推导和收窄，不根据 LLVM 类型判断语言类型相等。
- Typed IR 必须保留足够的语言语义信息，不能仅用相同的底层表示合并不同类型。
- lowering 根据已经确定的表示分类生成布局、GC 描述和目标代码，不重新解释源码类型规则。

因此，即使 `number` 与 `f64` 最终都降低为 LLVM `double`，checker 仍将它们视为不同类型；二者之间的转换由数值规范定义，而不是由 LLVM 表示决定。
