# 类型相等与规范化

- 规范状态：已定稿
- 实现状态：未实现
- 最后更新：2026-07-22
- 文档顺序：2

## 目标

定义 Nxts 的语义类型相等规则和 checker 规范化流程，并区分语义类型身份、运行时布局身份和运行时描述符身份。

## 身份层次

Nxts 分别处理以下三种身份：

| 身份             | 用途                                             | 是否决定语言类型相等 |
| ---------------- | ------------------------------------------------ | -------------------- |
| 语义类型身份     | checker 判断两个类型表达式是否表示同一类型       | 是                   |
| 布局身份         | 判断两个值是否可以共享字段偏移、大小、对齐和 ABI | 否                   |
| 运行时描述符身份 | GC、反射、属性枚举和运行时类型信息               | 否                   |

语义类型相同的值必须具有兼容布局，但不要求共享同一个运行时描述符。语义类型不同的类型也可能共享相同布局。

例如，可变对象类型和对应只读对象类型具有不同的语义类型，但可以共享布局；属性构造顺序不同的两个普通对象可以具有相同语义类型和布局，但使用不同的枚举描述符。

## 原子类型

内建原子类型使用稳定的语言类型标识判断相等：

```text
Boolean
Number
String
Symbol
Null
Undefined
I8 I16 I32 I64
U8 U16 U32 U64
F32 F64
USize ISize
Void
Never
```

底层表示不参与语言类型相等判断。两个类型即使都降低为 LLVM `double`，也不会因此自动相等。`number` 与 `f64` 是不同原子类型，不相等；二者之间的显式转换由数值类型规范定义。

`symbol` 是稳定的内建原子类型。每个 `unique symbol` 另有由模块身份和声明身份组成的单例语义类型标识；两个不同声明的 `unique symbol` 类型不相等，但它们与宽 `symbol` 可以共享完全相同的运行时布局。描述文本和运行时分配得到的具体 `SymbolId` 不参与静态类型相等判断。

## 类型别名

普通类型别名是透明的，不创造新的语义类型身份：

```ts
type UserId = i64;
type Identifier = UserId;
```

完成别名展开后，`UserId`、`Identifier` 和 `i64` 具有相同的规范类型。

checker 必须保留别名名称、声明位置和展开路径，用于诊断、调试信息和源码映射；这些信息不参与语义类型相等判断。

T28 的标准 `Brand<T, Tag>` 是专用静态类型构造器，不是普通别名声明产生的身份。品牌类型按“规范底层类型 + 规范标签类型”判断相等：

```text
Brand<T, A> == Brand<T, A>
Brand<T, A> != Brand<T, B>
Brand<T, A> != T
```

普通别名指向品牌时仍然透明，只保留目标品牌身份。品牌与底层 `T` 可以共享完全相同的布局、GC 描述和调用 ABI；运行时表示相同不使二者成为相同语义类型。

## 精确对象类型

普通对象类型采用精确结构相等。两个对象类型相等时必须满足：

- 属性集合相同。
- 对应属性使用相同的规范属性键。
- 对应属性类型相同。
- 对应属性的可选性相同。
- 对应属性的 `readonly` 权限相同。
- 已支持的其他对象成员分别满足其相等规则。

属性声明顺序不参与语义类型相等：

```ts
type PointA = {
  x: i32;
  y: string;
};

type PointB = {
  y: string;
  x: i32;
};
```

`PointA` 和 `PointB` 归一化为相同的规范对象形状。

可选属性和类型包含 `undefined` 的必选属性不相等：

```ts
type Optional = { value?: string };
type Required = { value: string | undefined };
```

可变属性和只读属性也不相等，但可以具有相同布局：

```ts
type Mutable = { value: string };
type ReadonlyValue = { readonly value: string };
```

二者之间是否允许单向赋值由类型兼容规范定义。

## 接口契约

接口身份由展平并规范化后的结构契约决定。契约成员集合、成员种类、规范键、成员类型、可选性、`readonly` 权限和泛型实参均参与相等判断；接口名称、声明模块、源码顺序和继承书写顺序不参与判断。

```ts
interface PointA {
  x: i32;
  y: string;
}

interface PointB {
  y: string;
  x: i32;
}
```

`PointA` 和 `PointB` 是同一个规范接口契约。接口继承只用于组合和约束契约，不引入名义身份。

接口契约与成员相同的精确对象类型不相等：

```ts
type PointObject = { x: i32; y: string };
interface PointContract {
  x: i32;
  y: string;
}
```

`PointObject != PointContract`。前者决定具体对象形状，后者表示携带底层对象引用和见证表的多态接口视图；二者之间的结构兼容和表示构造由 T03 与 T29 定义。

## 字典类型

字典身份由规范键域、值类型、写权限和显式固定成员契约共同决定。索引参数名称、声明顺序、初始容量、哈希种子和来源表示不参与类型身份。

原生字典与对象字典视图可以具有相同语义字典类型，但使用不同运行时表示；对象视图保留底层具体对象身份，不因此与原对象精确形状成为相同类型。字符串与数值索引签名的重叠规范化、固定成员约束和只读身份由 [`18-dictionaryTypes.md`](./18-dictionaryTypes.md) 定义。

## 类类型

类实例类型采用名义身份。身份至少包含稳定的模块身份和类声明身份：

```ts
class A {
  value: i32;
}

class B {
  value: i32;
}
```

即使 `A` 和 `B` 的字段完全相同，它们也不是同一类型。派生类与基类也不是同一类型；继承只建立由类兼容规范定义的关系。

编译过程内的类 `TypeId` 不作为跨模块稳定身份。跨模块编码由类型 ABI 规范定义。

## 字面量类型

字面量类型使用“基础类型或原生标量类型 + 规范值”判断相等：

```text
BooleanLiteral(true)
StringLiteral("ready")
NumericLiteral(i32, 200)
```

字面量类型与其基础类型不相等。字符串字面量按规范 UTF-16 code unit 序列判断身份；数字字面量的基础数值类型也是身份的一部分，数学值相同的 `i32`、`f64` 和 `number` 字面量仍是不同类型。

静态类型身份将 `-0` 与 `0` 规范为同一零字面量；Typed IR 仍须为 `number`、`f32` 和 `f64` 常量保留实际负零位语义。`NaN`、`Infinity` 和 `-Infinity` 不构成独立字面量类型。完整规范值和负数字面量规则由 T20 与数值规范定义。

## 复合类型

复合类型按“类型构造器身份 + 规范化类型参数或成员”判断相等：

`Array<i32>` 与 `Array<string>` 不是相同类型。

函数、字典、数组、元组、联合和泛型实例的成员相等规则由各自能力规范定义；交叉类型的身份和规范化见 [`14-intersectionTypes.md`](./14-intersectionTypes.md)。成员类型在参与比较前必须完成递归规范化。

递归类型使用有限符号图、类型替换边和按需具体实例表示，不能通过无限展开的类型树判断相等。递归类型的合法形式和等价算法由 [`19-recursiveTypes.md`](./19-recursiveTypes.md) 定义。

## 对象属性顺序

对象属性顺序不参与语义类型相等。checker 只按规范属性身份、类型、可选性和写权限判断对象类型身份：

```ts
const a = { x: 1, y: 2 };
const b = { y: 2, x: 1 };
```

`a` 和 `b` 可以具有相同语义类型，同时保留不同的 JavaScript 属性枚举顺序。枚举、删除和重新插入的用户可观察规则由 [`4-objectSemantics.md`](../semantics/4-objectSemantics.md) 定义；字段布局由 [`1-typeRepresentation.md`](../../compiler/representation/1-typeRepresentation.md) 定义；描述符和实例状态由 [`3-objectRuntime.md`](../../runtime/objects/3-objectRuntime.md) 定义。

## 规范化流程

checker 按以下顺序构造规范类型：

```text
源码类型表达式
  -> 名称解析
  -> 展开透明类型别名
  -> 规范化精确对象或展平接口继承契约
  -> 规范化 Brand 的底层类型和标签类型
  -> 递归规范化成员类型
  -> 构造规范类型图
  -> 类型驻留与编译过程内 TypeId 分配
```

规范化过程必须满足：

- 相同语义类型得到同一种规范结构。
- 属性源码顺序和别名拼写不影响精确对象身份；接口名称、来源和继承书写顺序不影响接口契约身份。
- 源码名称、声明位置和展开路径作为来源信息单独保留。
- 非法别名循环和不受支持的类型表达式在生成有效规范类型前产生诊断。
- 规范类型使用图结构，为递归类型和共享子结构预留稳定表示。

## 实现边界

checker 驻留、进程内 `TypeId`、规范键、关系缓存和复杂度预算由 [`5-checkerSemanticModel.md`](../../compiler/frontend/5-checkerSemanticModel.md) 定义。进程内 `TypeId` 不是稳定语言身份，不能写入模块接口或参与跨进程兼容判断。

跨模块 `SemanticTypeId`、类型指纹、版本兼容和描述符链接由 [`1-typeAbi.md`](../../compiler/abi/1-typeAbi.md) 定义；布局与 runtime 描述符只能在语义类型身份确定后生成。
