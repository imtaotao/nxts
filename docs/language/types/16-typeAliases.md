# 类型别名

- 规范状态：已定稿
- 实现状态：未实现
- 最后更新：2026-07-22
- 文档顺序：16

## 目标

定义 `type` 声明的命名、身份、泛型实例化、递归和导出规则，使所有已支持的类型表达式都能获得稳定名称，同时不改变目标类型的兼容性、布局和运行时成本。

类型相等见 [`2-typeIdentity.md`](./2-typeIdentity.md)，赋值兼容见 [`3-typeCompatibility.md`](./3-typeCompatibility.md)，对象类型见 [`15-objectTypes.md`](./15-objectTypes.md)，交叉类型见 [`14-intersectionTypes.md`](./14-intersectionTypes.md)。

## 核心原则

- 普通类型别名是透明别名，不创建新的名义类型。
- 别名右侧可以使用任意已受支持的类型表达式，但不能借别名绕过该表达式自身的限制。
- 泛型别名在使用点完成实参替换、约束检查和归一化，不保留动态泛型表示。
- 递归别名的每条循环路径都必须经过具有有限值表示的运行时引用间接层。
- 不可混用的静态身份使用标准 `Brand<T, Tag>` 幻象品牌；品牌不改变底层表示。
- 类型别名和品牌都不得引入包装、分配、tag、复制、运行时检查或额外 GC 状态。

## 基本语法

类型别名使用 TypeScript 的声明语法：

```ts
type UserId = i64;

type User = {
  id: UserId;
  name: string;
};

type Status = "pending" | "done";
```

别名声明只存在于类型空间，不生成运行时值。

## 普通别名身份

普通别名引用与目标类型归一化为同一语义类型：

```ts
type UserId = i64;

const id: UserId = 1;
const raw: i64 = id;
```

`UserId` 和 `i64` 可以直接互相赋值。字面量、运算、联合归一化、泛型推导、对象布局和 ABI 均按 `i64` 处理，不生成转换代码。

别名链同样透明：

```ts
type A = i64;
type B = A;
type C = B;
```

`A`、`B`、`C` 和 `i64` 具有同一规范类型身份。编译器可以保留源码别名链用于诊断，但不能让链长度或声明顺序影响类型相等、布局或代码生成。

## 名称空间与绑定

Nxts 使用与 TypeScript 一致的类型空间和值空间：

| 声明                       | 占用空间     |
| -------------------------- | ------------ |
| `type`、`interface`        | 类型空间     |
| `const`、`let`、`function` | 值空间       |
| `class`                    | 类型和值空间 |

同一作用域中的类型名称和值名称可以相同：

```ts
type Config = { debug: boolean };
const Config = { debug: false };
```

名称解析根据语法位置选择对应空间。类型位置中的 `Config` 引用类型别名，表达式位置中的 `Config` 引用值。

类型别名不参与声明合并。同一类型空间内，别名与别名、接口或类发生重复名称时产生编译错误。嵌套作用域分别遮蔽类型名称和值名称；具体词法作用域、导入符号绑定和重复声明诊断由 T57 定义，模块解析、导出图和跨模块可见性由 T55 定义。

`typeof` 类型查询是从值空间引用值绑定并产生类型的明确桥梁，由 T40 定义。Nxts 不支持 TypeScript 的 `namespace` 声明空间。

## 别名右侧

别名右侧可以使用 Nxts 已支持的任意类型表达式，包括基础类型、原生类型、字面量、对象、接口、联合、交叉、函数、数组、元组、类、泛型实例和其他别名。

别名只提供名称，不改变目标表达式的合法性：

```ts
type Empty = {}; // 编译错误：类型位置禁止裸 {}
type Unsafe = any; // 编译错误：any 永久不支持
type Huge = bigint; // 编译错误：bigint 当前不支持
```

条件类型、映射类型、模板字面量类型等能力只有在对应规范允许时才能出现在右侧；写入别名不会使未支持的类型构造变为合法，也不能绕过类型所在位置的限制。

位置受限类型可以获得名称，但展开后仍按目标位置检查：

```ts
type NoResult = void;

function log(): NoResult {}
let value: NoResult; // 编译错误：void 不能作为普通存储类型
```

checker 必须先解析并展开别名，再执行位置合法性检查。不能仅根据别名名称跳过 `void`、`never` 或其他目标类型规则。

## 泛型类型别名

类型别名支持类型参数、`extends` 上界约束和默认类型实参：

```ts
type Box<T> = { value: T };
type Entity<T extends { id: i64 }> = { value: T };
type Result<T, E = string> = { ok: true; value: T } | { ok: false; error: E };
```

规则如下：

| 场景     | 规则                                                                 |
| -------- | -------------------------------------------------------------------- |
| 约束     | 每个实参必须满足对应 `extends` 上界。                                |
| 默认实参 | 默认类型自身必须满足约束；省略时按声明顺序填入。                     |
| 必选实参 | 没有默认值的实参必须显式提供，不从别名赋值位置反向推导。             |
| 实例化   | 先绑定实参并检查约束，再替换参数、展开别名并执行完整类型归一化。     |
| 方差     | 默认按展开目标推导；可选 `in` / `out` 只校验结果，不能改变透明兼容。 |
| 高阶类型 | 不支持类型别名的部分应用、高阶类型参数或高阶类型构造器。             |

普通泛型声明中的 `extends` 只表达上界约束，不会自行触发条件分支或 `infer`。显式条件类型和类型级模式匹配由 [T41](./27-advancedTypes.md) 定义。

泛型别名实例在进入布局和代码生成前必须得到具体语义类型。编译器不能使用擦除后的动态值、统一装箱或运行时类型参数表作为推导失败的兜底；单态化、实例共享和代码体积预算由 T37 定义。

类型别名可以使用 TypeScript 的可选 `in`、`out` 和 `in out` 标记，但普通别名必须保持透明。标记与展开目标的推导结果一致时接受；试图主动收紧或放宽兼容关系时编译错误。需要固定泛型契约时使用接口，需要名义隔离时使用 `Brand`。

## 递归类型别名

递归别名合法的前提是每条递归循环都经过对象、数组、函数或其他已定义为运行时引用的间接层，使单个值具有有限布局：

```ts
type Node = {
  value: i32;
  next: Node | null;
};

type List<T> = {
  value: T;
  next: List<T> | null;
};

type Handler = () => Handler;
```

以下透明循环在编译期拒绝：

```ts
type A = A;

type B = C;
type C = B;

type Value = Value | i32;
```

联合、交叉或另一个别名本身不算运行时间接层。编译器不能通过隐藏装箱使非法递归变为合法。`Loop<T>`、`Loop<T[]>` 一类不断改变实参的递归声明使用有限符号图和类型替换边表示，具体实例按需创建；只有实际类型运算或代码生成要求无限实例时，才在触发位置编译报错。

checker 使用别名依赖图和强连通分量检测循环，把合法递归建立为稳定的符号类型图，而不是无限文本展开。递归类型比较必须对已访问的类型节点对做记忆化。递归等价、可构造性、数组与元组回边、泛型惰性实例化、增长检测、布局和 GC 描述由 [`19-recursiveTypes.md`](./19-recursiveTypes.md) 完整定义。

## 幻象品牌

普通 `type` 始终透明。需要防止相同底层类型被误用时，使用标准类型库提供的 `Brand<T, Tag>`：

```ts
type UserId = Brand<i64, "UserId">;
type OrderId = Brand<i64, "OrderId">;

const useBrand = (value: i64) => {
  const userId = value as UserId;
  const raw: i64 = userId;
  const orderId: OrderId = userId; // 编译错误：品牌不同
};
```

`Brand<T, Tag>` 是 TypeScript 常见 `unique symbol` 幻象属性品牌写法的编译器内建形式。TypeScript 工具侧的标准声明可以使用等价的私有 `unique symbol` 属性表达，但该声明不属于 Nxts 用户源码。

Nxts 不因此开放一般 symbol 属性键或任意“基础类型与对象”交叉。checker 只把标准库身份确定的 `Brand` 识别为品牌类型，并保存底层类型 `T` 与标签类型 `Tag` 的规范身份。

底层 `T` 必须在实例化和规范化后是非空、可存储且具有确定运行时表示的静态类型。`null`、`undefined`、`void`、`never`、`unknown` 不能直接作为品牌底层；规范结果仍以 `null` 或 `undefined` 为顶层成员的联合也不能作为品牌底层。`any` 和 `bigint` 已由各自规范拒绝。`Tag` 只参与规范类型身份，可以使用任意已支持且能够规范化的类型，不要求具有运行时表示。

品牌遵循以下规则：

- 品牌身份由规范化后的 `Tag` 决定，不由 `UserId` 等别名声明身份决定；相同 `T` 和 `Tag` 表示同一品牌。
- 品牌值可以隐式转换为底层 `T`，该方向只丢弃静态品牌信息。
- 底层 `T` 不能隐式转换为品牌；只有源类型与 `T` 兼容且运行时表示相同时，才允许使用 `as` 明确建立品牌。
- 不同品牌不能互相赋值。需要转换时必须先显式回到底层类型，再明确建立目标品牌。
- 品牌标记不能读取、写入、枚举或反射，也不影响对象键、运算语义和运行时类型判断。
- 运算结果按底层类型的运算规则确定，默认不自动保留品牌；具体结果类型由 T50 定义。

品牌在 Typed IR 和运行时中完全擦除，使用 `T` 的原生布局、寄存器传递方式、GC 描述和 ABI，不生成字段、包装、tag、分配或运行时检查。`as` 的统一断言边界由 T43 定义，`Brand` 的标准库声明身份由 T49 定义。

## 精确对象与接口别名

类型别名可以命名精确对象形状或接口契约：

```ts
type Point = {
  x: i32;
  y: i32;
};

interface User {
  id: i64;
}

type UserAlias = User;
```

checker 保留目标类型类别并复用其语义表示。`Point` 是精确对象类型；`UserAlias` 与 `User` 是同一个接口契约，不会因为经过 `type` 别名而变成精确对象。

别名本身不增加包装、运行时身份、独立布局或新的兼容关系。目标为接口时，值仍使用 T29 的接口视图，具体对象进入该目标仍生成 `InterfacePack`；这属于接口目标的既有成本，不是别名成本。

## 与 TypeScript 的兼容性

Nxts 保持 TypeScript 的 `type` 语法、透明别名、类型和值双空间、泛型参数、`extends` 约束、默认实参和常见品牌使用方式。通过 Nxts checker 的别名源码，在提供 Nxts 标准类型声明后也应通过 TypeScript 类型检查。

主要差异如下：

| 场景            | TypeScript                                       | Nxts                                                      |
| --------------- | ------------------------------------------------ | --------------------------------------------------------- |
| 别名右侧        | 支持完整 TypeScript 类型级语言。                 | 只接受 Nxts 已定义的类型构造。                            |
| `any`、`bigint` | 可以作为别名目标。                               | 分别永久拒绝和当前拒绝。                                  |
| 裸 `{}`         | 表示非 nullish 值的宽类型。                      | 类型位置直接拒绝。                                        |
| 非间接递归      | 直接别名循环通常报错，复杂类型计算可能延迟诊断。 | 每条循环必须经过运行时引用间接层。                        |
| 品牌实现        | 通常使用交叉和幻象属性约定。                     | 只支持标准 `Brand<T, Tag>` 特例，不开放任意幻象属性交叉。 |
| 方差标记        | 可以影响保留别名形式时的直接比较。               | 只校验展开目标，不改变透明别名兼容关系。                  |
| 运行时布局      | 类型整体擦除，由 JavaScript 动态值承载。         | 每个进入运行时的实例具有确定布局；别名和品牌保持零成本。  |

这些差异缩小 Nxts 接受的源码范围，不为相同 TypeScript 语法定义相反含义。

## 诊断与测试

至少覆盖以下场景：

| 场景                       | 预期                                             |
| -------------------------- | ------------------------------------------------ |
| 普通别名和多层别名链       | 与最终目标具有相同类型、布局和代码生成。         |
| 类型和值同名               | 按语法位置分别绑定。                             |
| 类型空间重复名称           | 编译错误，不进行别名或接口声明合并。             |
| 不支持或位置非法的别名目标 | 展开后在声明点或使用点产生明确诊断。             |
| 泛型约束与默认实参         | 按声明顺序检查并得到稳定规范实例。               |
| 泛型别名方差标记           | 与展开目标一致时接受；改变透明兼容时编译错误。   |
| 缺失必选类型实参           | 编译错误，不从使用位置隐式补全。                 |
| 合法引用递归               | 建立有限符号类型图，不无限展开。                 |
| 直接、互相或联合透明递归   | 编译错误，不隐藏装箱。                           |
| 不断改变实参的递归声明     | 声明与有限使用合法，具体实例按需创建。           |
| 无界类型计算或代码专门化   | 在触发位置编译错误并报告实例增长路径。           |
| 非法品牌底层类型           | 在品牌实例化处编译错误，不改变或过滤底层成员。   |
| 相同标签品牌               | 类型兼容并使用相同底层表示。                     |
| 不同标签品牌               | 赋值错误；不能直接互转。                         |
| 底层值建立品牌             | 只接受表示相同的明确 `as`，不生成运行时代码。    |
| 品牌属性访问、枚举或反射   | 编译错误，不产生运行时品牌字段。                 |
| 别名与品牌跨模块使用       | 静态身份一致，运行时布局与直接使用底层类型一致。 |
